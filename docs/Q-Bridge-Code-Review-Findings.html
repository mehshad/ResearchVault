Rate-limit POST /api/auth/login and finish AC-04 password hashing

#4 · backend · effort medium

The local/LDAP login handler at server/auth.ts:780-838 has no per-IP or per-account throttle and no lockout; package.json contains no express-rate-limit or equivalent. Combined with AC-04, which is still open exactly as registered (hashPassword at server/auth.ts:114-116 is a single unsalted SHA-256, compared with plain !== at line 802), an online guess is cheap and an offline crack of a leaked hash is cheaper. Fix: add express-rate-limit keyed on ip+username to /api/auth/login (and the LDAP path, which otherwise lets the app be used to brute-force directory accounts), and migrate to bcrypt/argon2 with rehash-on-login as the register recommends. The same limiter belongs on the OCR routes (tesseract.js and pdf-parse at routes.ts:1668 and 1817), the ORCID/Crossref/PubMed/OpenAlex discovery routes and the 50mb /api/bulk-data uploads, all currently unbounded; threat_model.md's Denial of Service section already requires it. Add helmet for baseline headers while there.

Refuse an administrator demoting themselves or the last administrator

#25 · backend · effort low

PATCH /api/admin/users/:id/role (server/routes.ts:11891-11935) and PUT /api/admin/users/:id/secondary-roles (11792-11888) never compare :id with req.session.user.id and never count how many administrators would remain. Because refreshSessionAuthorization rebuilds the principal on every request (server/auth.ts:616-648), an admin who moves their own primary role to 'user' and clears their secondaries is locked out on the very next call, and if they were the only admin nobody can undo it through the interface. This is the one path that locks out an administrator. Fix: reject the request when the target is the caller and the result would remove administrator rights, and when the target is the last account holding admin or superadmin.

Add an Origin/Referer check as a second CSRF layer beside SameSite=Lax

#47 · backend · effort low

CSRF protection currently rests entirely on the session cookie's sameSite: 'lax' (server/index.ts:117-121); there is no token and no Origin check, and package.json has no csurf/helmet. Lax does block cookie-bearing cross-site POST/PUT/DELETE in current browsers, but express.urlencoded is enabled (index.ts:66) so a form-encoded cross-site POST would parse if the cookie ever arrived, and the app sits behind nginx where a misconfigured APP_URL leaves secure: false. A cheap belt-and-braces fix is a small middleware on /api that rejects state-changing requests whose Origin (or Referer) host does not match APP_URL.

#37 · backend · effort low
