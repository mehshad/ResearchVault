01 Scope and method

This register covers authorisation only: the decision, once a request arrives, about whether the caller may proceed. Authentication mechanics, transport security, and data retention are out of scope.

Findings were established by reading the server and client source at the commit above and by querying a database restored from a production export. Where a number appears in this document it was counted from the code, not estimated; section 09 lists the commands so any statement here can be re-derived independently.

Authorisation in this system is decided in four distinct places. They are documented in turn, and they do not agree with one another — which is the substance of section 07.

02 Identity and authentication modes

A single environment variable, AUTH_MODE, selects how users are identified. One of the four values disables authorisation across the entire application.

ModeIdentity sourceEffect on authorisationFit for production

local Username and password in users, SHA-256 hashed Full enforcement Weak hashing
ldap Directory bind; local record created on first login Full enforcement Yes
oidc Identity provider; local record created on first login Full enforcement Yes

Session integrity

Every request to /api re-reads the signed-in user from the database before the route runs. A deleted account is rejected with 401 on its next request, and a role change takes effect immediately rather than at next sign-in. If that lookup fails the request is refused with 503 — the control fails closed, which is the correct behaviour.

Sessions are stored in PostgreSQL when DATABASE_URL is set and in process memory otherwise. Cookies are marked secure only when APP_URL begins with https://, so a deployment behind TLS-terminating infrastructure that advertises an http:// URL will issue non-secure session cookies.

Privileged bootstrap

The address in SUPER_ADMIN_EMAIL is promoted to superadmin on every login, not only at first sign-in. Whoever controls that environment variable controls the highest privilege in the system, and a demotion performed in the interface is silently reversed the next time that person signs in.

03 The role model

Two families of role coexist. Three built-in roles are defined in code and sit outside the configurable matrix; the access roles are rows in the database and are what the matrix configures. A person holds one primary access role plus any number of secondary roles, and their access is the union of all of them.

An access role is not the same thing as a job title. There are eighteen job titles on people's profiles and thirteen access roles, because six bench and support titles share the single Researcher role.

Every account starts restricted. New LDAP and OIDC users are provisioned as user, which is denied by default: a global policy blocks all API access except an explicit allowlist — their own profile, ordinary publication reads, impact-factor reads, certification modules, and registration. This is a genuine fail-closed default and it works as intended.

The thirteen configurable access roles are: IBC Board Member, IBC Officer, IRB Board Member, IRB Officer, IT Officer, Investigator, Lab Manager, Management, Outcome Officer, PMO Officer, Physician, Research Officer, and Researcher.

Access roles are not job titles

A person's job title is what they do; their access role is what they may reach. Keeping them as one list would make every distinction of seniority a distinct set of permissions to configure and keep in step, so six titles — Staff Scientist, Postdoctoral Researcher, PhD Student, Research Specialist, Research Associate and Research Assistant — resolve to the one Researcher access role. The titles themselves stand unchanged on profiles.

Investigator is deliberately not folded in. It carries responsibilities the others do not, and it is named directly by record-level policies (§06), so merging it would widen access rather than tidy it.

Consolidation fails closed. Holders of a retired role are not auto-mapped onto its replacement. They hold user — restricted by default — with their job title intact, so an administrator can see what each person actually does and make a deliberate assignment. Nobody keeps access through a role that does not exist.

A retired role's matrix rows merge into Researcher at the most permissive level any of them holds, so no remaining holder loses access. That has a consequence worth stating: against a database whose matrix was generated rather than configured, the merge propagates generated values, not decisions.

Primary and secondary roles

People hold more than one position: a Physician who is also an Investigator, a bench scientist who also sits on the IBC board. Consolidation (above) does not address this — it reduces how many roles exist, not how many one person needs. A single role string cannot express it, so users.role carries the primary access role and user_role_assignments carries the secondaries.

  • Access is the union. The most permissive level any held role grants wins. A secondary can only widen access, never narrow it — there is a test asserting exactly that.
  • Administrator rights are normally secondary. admin is layered onto a job title rather than replacing it, so administrators keep their real role in the record.
  • The onboarding lockout lifts on assignment. The restricted user role confines its holder only while it is the only role held; granting any secondary counts as an assignment.
  • superadmin is unassignable — the endpoint refuses it explicitly, and it comes from SUPER_ADMIN_EMAIL alone.

One resolution module, shared/effectiveRoles.ts, answers both "what does this person hold" and "what does that add up to", so the guards, the matrix and the client cannot drift apart.

04 Fixed rules — the guard inventory

Guards are defined in code and cannot be changed without a deployment. Every one evaluates all roles a person holds, not the primary alone.

Only two of them decide anything from a role name. The rest resolve the permission matrix, which means an administrator changing a cell changes what the server admits — the thing a configurable matrix is supposed to mean. Every area they resolve is one the settings screen shows.

Two further middlewares run globally on every /api request: the session refresh described in section 02, and the restricted-role policy that confines the user role to its allowlist. Both are bypassed in demo mode. The session refresh also reloads secondary roles, so revoking one takes effect on that session's very next request rather than at next sign-in.

How a cell resolves

  • superadmin and admin short-circuit to edit before any lookup — in any role slot, primary or secondary.
  • A person holding several roles takes the most permissive level among them.
  • Outside demo mode, the user role resolves to view for publications and hide everywhere else, whatever the stored row says.
  • Otherwise the stored access level applies: hide, view, create, or edit.
  • A missing row resolves to hide — the default is closed, which is correct.

The matrix governs the API, not only the interface. All 18 areas are resolved by server-side guards covering 94% of routes, so a caller reaching the API directly meets the same cells the interface does; see section 07.

An unconfigured matrix stays unconfigured. Where nothing is stored, the settings screen renders a generated starting point, says plainly that it is not in force, and writes nothing until an administrator applies it — which stamps their account on every cell. Nothing seeds the matrix on its own.

This does not vouch for matrices already in a database. Anything stored before that behaviour changed may still be generated defaults that were written back silently, and it travels: an export carries the matrix, so a generated one survives a backup and restore intact. Any statement about what a particular role may reach must be read from the production database, not from a development copy, and a matrix that has never been reviewed should be treated as unreviewed however populated it looks.

The consolidated area set

The matrix configures 18 areas for 13 roles — 234 cells, complete, with no gaps. One definition governs: the client list is derived from the shared constants, so the set the matrix is seeded from and the set the settings grid renders cannot disagree, and no area can exist where an administrator is unable to see it.

A consolidated cell holds the most permissive level of its group. The merge widens rather than narrows, so nobody loses access they hold. Widening is visible in the grid and can be corrected there; silently narrowing would shut people out of screens they use with no trace of why. Review the consolidated pmo-office and research-office columns — a role with edit on any one of the folded areas holds it on the whole office.

Retired ids remain in use across the interface, so every lookup resolves through NAVIGATION_AREA_ALIASES on both the client and the server rather than each call site being rewritten — a missed one would fall through to hide.

Below role level, several policies decide access to individual records. These are enforced server-side and are among the stronger controls in the system.

The SDR exception

A publication is expected to link to a Scientific Data Record. A scientist may instead record why none applies — the case being work done for a collaborator at another institution, where no research activity exists here to link. The explanation replaces the link: it is required, bounded, and clears the missing-SDR flag as soon as it is given rather than when it is accepted.

The control is a reading, not a gate. There is no approval state. The Outcome Office reads the explanation on the publication card before finalising the record, and where it disagrees it sends the record back through the existing invalid/correction loop. An auditor should therefore treat the presence of an exception as a claim that was available to the office, not as one it endorsed — the endorsement is the finalisation itself. Each claim is written to the manuscript history with the account that made it, so who claimed what and when is recoverable.

publications.sdr_exemption_reason, _requested_by, _requested_at -- mutually exclusive with research_activity_id; linking an SDR clears all three

The eight that reach no guard are the ones that cannot: sign-in itself, registration, the liveness probe and object storage are all reached before a role exists, and guarding them would lock everyone out. They are listed in UNMAPPED_API_PREFIXES beside the reason each is excluded.

Five more sit in that list while still being guarded: /api/system-configurations has no matrix area but is administrator-only through requireAdmin, in the same way as /api/admin and /api/bulk-data. Four presentation keys under it — theme name, institution labels, section visibility and default colour mode — are readable without a session, because the sign-in page applies them before anyone has said who they are.

Nothing else answers without an account. Verified by requesting all 127 GET routes against a running server in local mode with no cookie of any kind: the only JSON that came back was the liveness probe. A bare prefix such as /api/admin returns 200, but the body is text/html — the single-page-app catch-all, not an endpoint. Check the content type before reading such a result as an exposure.

The guards are additive, not alternative. A route under /api/publications carrying requirePublicationOfficer needs the publications area and the outcome-office area. That is what having two separately configurable areas is supposed to mean.

08 Findings

What is still open, most severe first. Findings are removed once they are fixed rather than marked closed — this is a list of work outstanding, not a record of work done. Identifiers stay stable so they can be carried across audits, and numbers are never reused.

AC-03

Demo mode disables authorisation entirely

High

With AUTH_MODE=demo there is no login, a guest user with the Management role is injected into every session, authentication passes unconditionally, the restricted-role policy short-circuits, and the session refresh is skipped. The guard requireAdmin additionally treats that demo Management session as an administrator.

Role emulation moves the session, not just the browser. The demo role selector posts to an endpoint that changes the session role, and accepts only a role that really exists, so the interface and the API agree about who you are. The endpoint is registered only when the mode is demo, so outside demo the path does not exist rather than existing and refusing — but it is one more thing that turns on with that single environment variable, which is the point of this finding.

This is deliberate and appropriate for a public demonstration instance. The risk is configuration, not code: a single environment variable separates a fully governed deployment from an ungoverned one, and nothing in the application prevents the combination of demo mode with a production database.

Recommendation Refuse to start in demo mode when the configuration looks like production, and surface the active mode in the interface where an auditor can see it.

AC-04

Local passwords are stored as unsalted SHA-256

High

In local mode, passwords are hashed with a single unsalted SHA-256 pass. That is fast to compute and therefore fast to attack offline, and identical passwords produce identical hashes across accounts.

Recommendation Move to a slow, salted algorithm — bcrypt, scrypt or Argon2 — rehashing on next successful login. Where LDAP or OIDC is available, prefer it and disable local accounts.

AC-05

Highest privilege is granted by environment variable, on every login

Medium

The address in SUPER_ADMIN_EMAIL is re-promoted to superadmin at each sign-in. Removing that privilege through the interface does not persist, and the grant lives in deployment configuration rather than in any record an auditor would examine.

Recommendation Treat it as a bootstrap: promote only when no superadmin exists, and log the promotion as an auditable event.
